## Working rules

Read README → CONTEXT → PLAN → TASKS → PROGRESS, then inspect the actual repository. Use stable task IDs in commits and handoffs. Follow dependencies; do not turn a missing prerequisite into an assumption. A source-audit dependency means inspect actual implementation, not just repeat this pack's README summary.

**Statuses:** `TODO` = not started; `IN_PROGRESS` = active with current evidence; `BLOCKED` = cannot finish because a named dependency/access decision is missing; `DEFERRED` = preserved for a later release with reason; `DONE` = acceptance verified; `REJECTED` = consciously excluded behavior, not implemented work.

DONE requires source code, acceptance checks, actual command/results, permission/security checks and updated progress. A UI mock, a generated test file, a copied README or successful authentication alone cannot close a feature task. Never test with real outbound applications, posts or unsolicited messages.

**Start here:** `FND-001`. Source audit tasks can proceed after the scaffold exists. Feature-specific tasks depend on the relevant donor audits. The final `SRC-GATE` checks full inventory coverage across all sources, not just README headings.

## How to interpret source picks

CONTEXT selects preferred **reference patterns**, not measured winners. Audit tasks must capture commit SHA, file/function, dependencies, implementation status, edge cases and destination. Record every discovered unique sub-feature as adopted, merged, deferred or rejected. Add a new stable task/feature ID when needed; do not overwrite an existing ID's meaning. For deferred work include the reason and re-entry prerequisite.

Feature IDs `CAR-*`, `LI-*`, `SOC-*` are defined in CONTEXT. Requirement IDs `REQ-*` are user/product constraints. Acceptance IDs `AT-*` are defined in PLAN. Their tables below form a machine-checkable traceability map.
